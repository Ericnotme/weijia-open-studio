# 有共鸣：产品方案 v0.1

## 给谁，解决什么

服务认真寻找长期关系、兴趣和经历丰富、却很难用几条条件介绍自己的人。他们需要的不只是被看见，还需要对方明白：这些细节怎样影响一起生活。

## 产品承诺

**把一个人的复杂，翻译成两个人一起生活的具体画面。**

用户获得三份可以修改和带走的成果：一份“像我”的介绍、一份有依据的相处提案、一份能落实的初次见面计划。

## 这次的 X 因素如何落地

| 用户的困扰 | 页面实际行为 | 得到的价值 |
| --- | --- | --- |
| 自我介绍像简历、参数表 | 兴趣与生活选择实时变成生活画像 | 让对方想象相处体验 |
| 不知道为什么推荐一个人 | 显示共同活动、城市条件、沟通和婚育差异 | 先知道值得聊什么 |
| 聊天拖很久也没见面 | 生成一小时或九十分钟的公共场所活动草稿 | 降低第一次见面的安排成本 |
| 被“匹配度”带着走 | 展示具体分歧、不计算分数 | 保留人的判断与退出权 |

## 原型体验路径

1. 打开主页，从“看看和你在一起的生活”进入体验。
2. 使用阿远示例，或填写自己的介绍；点击“从介绍中识别”，再手动确认兴趣。
3. 确认作息、城市、婚育与沟通方式。复制介绍或进入比较。
4. 夏宁展示“共同兴趣 + 可协商差异 + 婚育待确认”；周野展示“共同兴趣不能消除城市、婚育分歧”。
5. 选择活动、日期、时间、城市、时长与预算。生成、复制、下载提案或日历草稿。
6. 在真实见面后可以用三个反思入口整理感受；原型只展示提示并在当前页面记录选择。

## 最小验证实验（待执行）

招募 12–20 位自愿参与、希望认真交友的成年人。先仅验证表达和相处理解，避免承诺自动找到对象。

让每位参与者提供自己愿意分享的简介，再分别阅读原简介与整理后的画像；随机展示顺序，减少先入为主。所有分享需由本人确认具体内容和对象。

观察三个问题：

- “这像不像我？”受访者能否指出至少一个被准确表达的细节，是否需要大量纠正。
- “我知道可以聊什么了吗？”读者能否提出具体活动或重要差异问题。
- “我愿意进一步了解吗？”有真实双方同意的配对后，记录是否愿意见面、见面后是否双方都想继续。

记录纠正率、画像导出率、真实双方同意见面率和见面后双向继续意愿。小样本只用于寻找问题，不宣称已证明效果。不要用浏览时长代替关系质量。

## 后续开发顺序

第一阶段：验证文案是否准确、用户能否纠正，以及“相处提案”是否确实带来更具体的聊天。保留当前静态演示作为访谈工具。

第二阶段：仅在价值成立后建设双方同意分享的账户和数据系统、可撤回的档案授权、最少信息收集、屏蔽举报与内容审核。每条画像建议区分“本人填写”“本人确认”“待确认建议”。

第三阶段：接入受控的模型服务，严格约束输出结构，显示证据句与不确定性；在用户确认前不发出个人信息。不让模型依据健康、基因、外貌评分或未经证实的经济条件进行等级排名。

第四阶段：再决定 iOS 客户端与 App Store 发布。网页包装不等于已经具备独立应用价值；需要真实可维护的服务、可靠的账号与数据管理、手机交互与无障碍适配、隐私披露和运营支持。

## 商业假设

可验证一次性的画像整理与见面提案服务，或低频的认真交友会员。先观察用户愿意为哪一项确定价值付费；暂不设置价格，不出售个人数据，不以无休止滑动为目标。

## 当前验收边界

本地功能与核心规则可以使用；人物全部虚构；未接入模型、真实推荐、消息、支付或外部日历账号。生成日历文件只产生个人草稿。现阶段的验证结果不能推广为真实择偶准确率。
